- Reparada la inicialización JavaScript y el orden de dependencias de `api-fetch`, `private-apis` y `url`, manteniendo exclusiones acotadas de Rocket.
- Protegidos los scripts de recuperación para su uso previsto por CLI; no utilizar endpoints públicos como mecanismo de administración.
- Consolidados metadatos y schemas para reducir duplicidades; organización de Rank Math revisada.
- Corregida la modalidad de **MF0973_1: presencial**. No extrapolar esa modalidad a otros cursos.
- Corregido el horario de cierre a **20:00** y etiquetas de formularios CF7.
- Retirado GTM vacío y corregidos identificadores duplicados del megamenú.
- Producción tenía activada la opción nativa que desaconsejaba indexar. Se desmarcó en Ajustes → Lectura; la causa y el momento del cambio previo son desconocidos.
- Comprobados `index,follow`, canonical, robots y sitemap con solicitudes públicas independientes. No se debe restaurar `noindex` de producción al revertir otros ajustes.
- Añadido `/llms.txt` como índice de navegación Markdown: no concede autorización de rastreo o entrenamiento y no constituye una API de herramientas.

### Accesibilidad y presentación

- Añadidos un único landmark principal y salto al contenido con foco efectivo; el footer permanece fuera del principal.
- Corregidos encabezados mediante controles nativos de Elementor, conservando estilos. Footer y títulos de testimonios pasan a H3.

- WhatsApp conserva solo el logo en el lanzador, sin badges de estado ni tooltip «Pregunta a la IA». Apertura/cierre local comprobados sin enviar mensajes.
- Desactivada la pantalla splash móvil; portada mantiene plantilla `elementor_header_footer`, ancho completo y banner/header/footer, sin banda gris «Inicio» del tema.
- Reparado formulario móvil de portada: nombre, email, teléfono y consulta uno debajo de otro; consentimientos íntegros y cuadro RGPD ancho completo. A 360 px, ambos consentimientos ocupan dos líneas.
- Corregida la X del menú lateral quitando solo el fondo del botón, sin alterar sus eventos ni el aviso de cookies.

- Corregido el preload del hero y sus atributos; mantenidas exclusiones necesarias para Elementor y dependencias JavaScript.

### 3.1. Corrección posterior: navegación agéntica 2/3

El propietario aportó una captura de 2/3 después de este cierre. Se reprodujo en una auditoría pública nueva con Lighthouse 13.5.0: árbol de accesibilidad y CLS pasaban, pero `llms-txt` fallaba con «Timed out fetching resource». Las mediciones anteriores de cuatro categorías no incluían esta categoría; no servían para confirmar su estado final.

`/llms.txt` existía con contenido correcto, pero se generaba desde WordPress: una petición independiente tardó 3,04 s. Se creó **solo el archivo estático `llms.txt` en la raíz de WordPress de producción**, con el mismo contenido público. La comparación normalizando saltos CRLF/LF confirmó identidad de contenido; no se cambiaron permisos de rastreo ni se añadieron herramientas WebMCP.

La creación se realizó mediante fragmento administrativo temporal **17902**, restringido al dominio de producción y a administradores, con apertura exclusiva `xb` para no sobrescribir un archivo preexistente. El fragmento está **inactivo** tras la operación. No se modificaron configuración nginx/Plesk, cachés, cron, Redis, tema o BD completa.

Comprobación posterior: HTTP 200, `text/plain; charset=UTF-8`, respuesta de 73–88 ms en tres peticiones. **Dos auditorías públicas posteriores con perfiles nuevos: 3/3 (100) en ambas**, pasan árbol accesible, CLS y llms.txt; sin avisos de ejecución. No implica mejora de la velocidad general de la portada ni garantiza resultados futuros de otras herramientas.

**Mantenimiento:** fuente documental en [`content/llms.txt`](../content/llms.txt). La versión activa es el archivo estático de producción; cualquier cambio debe hacerse también allí. El antiguo callback WordPress permanece sin modificar como fallback de reversión, pero el servidor sirve el archivo estático antes de cargar WordPress. No reactivar 17902 como tarea periódica. Si fuera necesario revertir, retirar únicamente el archivo creado, con respaldo y autorización: volvería el endpoint dinámico anterior y posiblemente sus timeouts. No borrar otras rutas ni restaurar el tema.

## 4. CSS crítico: decisión y límite

- La entrega optimizada está marcada en Rocket, pero el HTML público comprobado no contiene el CSS crítico/used CSS generado esperado.
- El build instalado de WP Club modifica la URL del servicio SaaS frente al código oficial. La cola de generación había fallado o quedado pendiente. No se publican claves ni datos de licencia.
- Cambiar a «CSS asíncrono» no elimina por sí solo la dependencia del servicio externo de generación.
- No se pegó CSS crítico improvisado de la portada como fallback global, ni se recortaron estilos únicos sin validación.
- El propietario rechazó adquirir una licencia oficial y pidió dejar Rocket como está. **No se sustituye el plugin ni se reintenta esa optimización sin una nueva decisión.**

Referencias: [Remove Unused CSS](https://docs.wp-rocket.me/article/1529-remove-unused-css) y [Load CSS Asynchronously](https://docs.wp-rocket.me/article/1266-optimize-css-delivery).

## 5. Producción, clon y Laguna: no mezclar

| Entorno | Condiciones que deben conservarse |
| --- | --- |
| Producción | Rocket, Redis, SMTP y UpdraftPlus activos; Super Cache inactivo; indexación permitida |
| Staging | Raíz/BD independientes; noindex; Force Login, Disable Emails y guard de aislamiento activos |
| Caché del clon | Redis desconectado y drop-in retirado por renombrado; Rocket/Super Cache inactivos |
| Tareas del clon | `DISABLE_WP_CRON=true`; bloqueos de cron, colas, comunicaciones y actualizaciones automáticas del guard |
| Laguna | Restauración previa completada y acceso del administrador recuperado; no modificar para estos ajustes |
| Cron producción | Mantener tarea externa cada 10 minutos de `httpdocs/wp-cron.php`, PHP 8.3.35, y tarea propia de Laguna; no duplicarlas |

El guard del clon (17880) pasó sus diez comprobaciones de aislamiento. Sus restricciones cubren las API WordPress, pero no equivalen a un firewall completo: clientes cURL/SDK/SMTP independientes o ejecución manual requieren revisión adicional.

Axarnet reprodujo el fallo nginx 500 de protección HTTP y lo investiga. Con autorización del propietario se continuaron ajustes pequeños sin esa capa. Force Login protege páginas WordPress, **no todos los archivos estáticos**; estos pueden seguir públicos. No se afirma que el endpoint cron esté protegido por completo por devolver 200 a una petición HEAD.

**Nunca copiar guard, noindex, bloqueo de emails, Force Login, opciones del clon o su BD a producción.** Tampoco eliminar bases de datos porque Plesk las marque como «no asignadas».
